# Patternflow Ensemble — 패널 여러 대를 함께

패널 8대, 10대, 그 이상을 허브 하나에 묶는다. 어느 패널이든 노브를 돌리면 다른 패널들이 따라오는데, 바로 따라오게 할 수도 있고 지도에 놓아 둔 자리의 거리만큼 늦게, 물결처럼 퍼지게 할 수도 있다. 패널마다 다른 패턴을 줄 수도 있다. 노트북은 USB로 허브에 붙어서 배치와 규칙을 정하고, 무슨 일이 일어나는지 본다.

2026년 전시의 구성(패널 → FlowLocal → 노트북)과 같은 모양이다. 허브는 그때의 FlowLocal 보드(ESP32-S3-DevKitC-1) 그대로 쓴다.

> **2026-11-11 첫 판은 하드웨어 없이 만들었다. 2026-11-14 처음 보드에 올렸다.** 허브 한 대와 패널 두 대가 허브의 핫스팟으로 묶였고, 한 패널을 돌리면 다른 패널이 따라온다. 무엇이 실기로 확인됐고 무엇이 아직인지는 [8장](#8-아직-실기로-확인-안-된-것)에 있다.

## 1. 지금 바로 보기

보드 없이 된다. Chrome이나 Edge에서 [`console/index.html`](console/index.html)을 연다(파일을 끌어다 놓으면 된다).

가상 패널 10대가 뜬다. 허브와 패널 펌웨어에 들어가는 코드를 그대로 브라우저에서 돌리는 것이라, 여기서 보이는 동작이 보드가 할 동작이다. 지도의 패널을 눌러 고르고 오른쪽의 "손으로 돌리기"를 누르면 그 패널 앞에 선 사람이 된다. 왼쪽에서 K1~K4와 패턴을 각각 단독·동시·물결로 바꿔 본다. 패널을 끌어 자리를 옮기면 물결이 닿는 순서가 바뀐다. 손실 슬라이더를 올리거나 패널 전원을 껐다 켜도 결국 같은 상태로 모인다.

지도의 패널은 패턴의 그림이 아니라 정보다: 패널 번호, 패턴 번호(`P3`), K1~K4의 위치를 막대로, 확대하면 그 아래 패턴 이름.

## 2. 구조

```
 패널 1 ─┐
 패널 2 ─┤  Wi-Fi, UDP 7400 (PFE/1)        ┌─ USB 잭: 케이블 하나로 콘솔(시리얼) + MIDI + 굽기 ─ 노트북
   …     ├──────────────────────── 허브 ───┤
 패널 N ─┘  ESP32-S3-DevKitC-1              ├─ COM 잭: 부팅 로그. 안 꽂아도 된다 (콘솔도 붙을 수 있다)
                                            └─ Wi-Fi: http://192.168.66.1/ 에서 같은 콘솔 (전화기용)
```

**패널**은 Patternflow 펌웨어에 `ensemble` 기능을 얹은 것이다. 노브마다 위치 하나(0~1000)를 갖고, 전시 패널이 그랬듯 그 위치를 lane으로 패턴에 넘긴다. 패턴의 매개변수는 그 위치를 자기 범위에 옮긴 값이 된다. 클릭 수가 아니라 위치를 주고받기 때문에 패널끼리 어긋나지 않는다. 패널은 0.5초마다, 그리고 손이 움직일 때마다 자기 상태를 허브에 알리고, 허브가 말한 상태로 간다.

**패턴이 바뀔 때 패널에 이름이 뜨지 않는다.** 혼자 쓰는 Patternflow 패널은 패턴이 바뀌면 그 이름을 1초 보여 주는데, 벽에서는 바꿀 때마다 모든 패널에 글자가 지나가게 된다. 앙상블 이미지는 누가 바꿨든(허브, 콘솔, 패널의 K4) 이름을 띄우지 않는다(v0.1.7부터. 되살리려면 `PF_ENSEMBLE_PATTERN_NAME 1`).

**손이 이긴다.** 노브마다 손이 움직인 횟수를 세고, 허브는 "이 값은 네 n번째 움직임까지 보고 정한 것"이라고 함께 보낸다. 횟수가 다르면 패널은 그 값을 버린다. 그래서 돌리는 도중에 허브가 옛 값으로 끌어당기는 일이 없다.

**허브**는 패널마다 "있어야 할 상태"(패턴 하나, 노브 넷)를 들고 있다. 채널은 다섯(K1, K2, K3, K4, 패턴)이고 채널마다 규칙이 하나다.

| 규칙 | 한 패널을 돌리면 |
|---|---|
| 단독 | 그 패널만 바뀐다 |
| 동시 | 묶인 패널이 모두 바로 바뀐다 |
| 물결 | 돌린 패널에서 시작해, 각 패널에 `거리 ÷ 속도`만큼 늦게 닿는다 |

거리는 콘솔 지도에 놓은 자리에서 나온다. 한 칸이 기준 간격이고, 속도 2칸/초면 한 칸 떨어진 패널이 0.5초 뒤에 따라온다. 두 사람이 양쪽 끝에서 돌리면 물결이 엇갈려 지나가고, 다 닿고 나면 모든 패널이 마지막에 돌린 값을 보여 준다.

K4는 두 가지로 쓴다. 패턴을 넘기는 손잡이(세 클릭에 한 패턴, 전시 때와 같다)이거나 네 번째 노브다. 콘솔의 K4에서 고른다. 패턴을 넘기는 동안에는 패턴의 네 번째 값이 가운데(500)에 머물고, 콘솔의 규칙에서 K4의 줄은 "K4 패턴"이 된다. 네 번째 노브로 쓰면 K4도 K1~K3처럼 퍼지고, 패턴은 패널에서 K4를 1초 길게 눌러(Patternflow의 SELECT 화면) 고르거나 콘솔에서 고른다. 패널에서 고른 패턴도 패턴 규칙대로 다른 패널에 전해진다.

주고받는 것은 언제나 상태 전체다. 패킷 하나를 잃어도 다음 것이 같은 내용을 가져오고, 전원이 나갔다 들어온 패널은 한 번에 지금 상태를 다시 받는다. 허브가 꺼졌다 켜지면 배치와 규칙은 플래시에서 돌아오고, 패널들은 보던 것을 그대로 보여 준다.

**같은 코드가 세 군데서 돈다.** [`core/`](core/)의 헤더들은 Arduino도 libc도 쓰지 않는다. 허브 펌웨어와 패널 펌웨어가 그대로 포함하고, PC 테스트가 그대로 컴파일하고, 콘솔의 데모가 WebAssembly로 그대로 돌린다.

통신 규약은 [`PROTOCOL.md`](PROTOCOL.md)에 있다.

## 3. 허브 굽기

보드는 ESP32-S3-DevKitC-1 한 장, 붙이는 것 없음. 전시 때 FlowLocal로 쓴 보드면 된다.

```bash
cd ensemble/hub
cp hub_secrets.example.h hub_secrets.h     # 핫스팟 이름과 비밀번호를 적는다 (커밋되지 않는다)
python -m platformio run -e hub
python -m platformio run -e hub -t upload --upload-port COMx    # USB 잭의 포트 (처음 한 번은 COM 잭의 포트)
```

- 플랫폼은 패널 펌웨어와 같은 `espressif32@7.0.1`이라, 패널을 빌드해 본 컴퓨터면 더 받을 것이 없다.
- 저장소 경로에 한글이 있으면 링커가 못 쓴다. 전시 때처럼 `PLATFORMIO_BUILD_DIR`을 영문 경로로 잡는다.
- **케이블은 USB 잭 하나면 된다.** 노트북에 꽂으면 `Patternflow Ensemble`이라는 시리얼 포트(콘솔이 붙는 곳)와 MIDI 장치(5½장)가 함께 생기고, 굽기도 이 잭으로 한다. PlatformIO가 그 시리얼 포트를 1200 bps로 한 번 열면 허브가 다운로드 모드로 재시작하고(버튼을 누를 일이 없다), 그때 나타나는 포트로 올린 뒤 허브가 다시 켜진다. **COM 잭**은 부팅 로그(115200)이고 안 꽂아도 된다. 이 펌웨어가 한 번도 올라간 적 없는 보드는 처음 한 번만 COM 잭으로 굽는다.
- USB 잭 하나에 시리얼과 MIDI를 함께 싣는 데는 손이 갔다. Arduino 코어 2.0.x에 든 USB 드라이버가 두 코어에서 안전하지 않고 송신 버퍼의 자리도 잘못 잡아서, 둘을 같이 쓰면 한쪽이 영영 멈추거나 서로의 바이트가 섞였다. 허브가 하는 일은 [`hub/src/usb_s3.cpp`](hub/src/usb_s3.cpp) 맨 위에 적혀 있다. 고쳐 쓸 때 알아 둘 것은 `platformio.ini`의 `-Wl,--wrap=xTaskCreatePinnedToCore` 한 줄이 그 일부라는 것이다.
- 켜고 12초 뒤에 핫스팟이 뜬다. 허브가 다시 켜질 때 앞서 붙어 있던 패널이 끊긴 것을 알아차릴 시간이고, 전시 때 FlowLocal에서 잰 값을 그대로 가져왔다(`HUB_AP_START_DELAY_MS`). USB와 콘솔은 그동안에도 된다.
- 설정은 [`hub/hub_config.h`](hub/hub_config.h)에 있다. 주소는 FlowLocal과 같은 `192.168.66.1`이다.

## 4. 패널 굽기

패널 펌웨어는 공개된 [Patternflow](https://github.com/engmung/Patternflow) 소스에 폴더 둘을 더한 것이다. 코어 파일은 하나도 고치지 않는다.

```bash
git clone https://github.com/engmung/Patternflow patternflow      # 이 저장소 안에 두면 .gitignore가 가려 준다
python ensemble/panel/install.py patternflow
cp firmware/patternflow_secrets.example.h patternflow/firmware/patternflow/patternflow_secrets.h
#   PF_WIFI_SSID / PF_WIFI_PASS 를 허브의 것과 같게 적는다
cd patternflow
PF_BUILD_DIR=$HOME/pf-build ./firmware/bundles/build.sh ensemble
```

`install.py`가 넣는 것은 `firmware/patternflow/features/ensemble/`(기능과 `core/`의 헤더 셋)와 `firmware/bundles/ensemble/`(빌드를 정하는 파일 둘)뿐이다. 나오는 이미지는 `$PF_BUILD_DIR/firmware/firmware.bin`이다.

- 이 빌드에는 `ensemble`만 들어 있다. OSC, MQTT, 네트워크 MIDI는 저마다 노브와 패턴을 움직이기 때문에, 함께 넣으려면 누가 이끄는지부터 정해야 한다.
- 전시용 패치(`firmware/panel-exhibit-2026.patch`)와는 따로다. 그 패치의 작가 패턴 여섯과 한 이미지에 넣는 것은 아직 해 보지 않았다.

### Wi-Fi로 올리기

USB는 필요 없다. 에디션을 바꿀 때와 같은 길이다. Patternflow 코어에는 `/update`가 있고, 이 빌드는 코어를 건드리지 않으니 들어갈 때도 나올 때도 그 길을 쓴다. 패널과 같은 Wi-Fi에 있는 컴퓨터에서 한다.

여러 대는 [`tools/panels.py`](tools/panels.py)로 한 번에 한다. Python만 있으면 되고 따로 깔 것은 없다.

```bash
python ensemble/tools/panels.py scan -o panels.txt                             # 이 네트워크의 패널을 찾아 목록으로
python ensemble/tools/panels.py flash $HOME/pf-build/firmware/firmware.bin     # 목록의 패널 전부에 올린다
python ensemble/tools/panels.py status                                         # 무엇이 돌고 있는지
```

`flash`는 조심해서 올린다. 켜지지 않는 이미지는 Wi-Fi로 되돌릴 수 없기 때문이다.

- 올리기 전에 파일을 본다. ESP32-S3 앱 이미지가 아니거나, 패널의 3 MB 자리보다 크거나, `/update`가 들어 있지 않으면(허브 펌웨어를 잘못 고른 경우) 보내지 않는다.
- 이미 그 이미지를 돌리는 패널은 건너뛴다. 그래서 중간에 실패하면 같은 명령을 다시 돌리면 되고, 남은 패널만 올라간다.
- 첫 한 대를 먼저 올리고, 다시 켜져서 10초 동안 그대로 있는지 본 뒤 나머지를 올린다. 돌아오지 않는 패널이 나오면 그 자리에서 멈추고 다음 패널에는 손대지 않는다.

**그래도 첫 한 대는 USB를 꽂을 수 있는 패널로 한다.** 이 이미지는 아직 보드에서 켜 본 적이 없다. 켜지다 멈추면 그 한 대는 USB로 다시 구워야 한다([patternflow.work/flash](https://patternflow.work/flash)). `panels.txt`의 맨 윗줄이 첫 대다.

패널을 고르는 방법은 넷이다: 명령 뒤에 주소를 적거나, `--hub <허브 주소>`(허브가 아는 패널, `--only 1,3`으로 번호를 고른다), `--file <목록>`, 아무것도 없으면 지금 폴더의 `panels.txt`. 주소는 IP거나 `patternflow-a1b2.local`처럼 MAC 끝 네 자리가 붙은 이름이다. `patternflow.local`은 모든 패널이 함께 쓰는 이름이라 여러 대가 켜져 있으면 어느 패널이 답할지 모른다.

한 대만이면 도구 없이도 된다. 브라우저에서 `http://<패널 주소>/update`를 열어 `firmware.bin`을 끌어다 놓거나, 빌드까지 한 번에 `./firmware/bundles/build.sh ensemble flash <패널 주소>`.

패턴, 저장된 Wi-Fi, 밝기, 노브 설정은 그대로 남는다. 파티션 표가 같고 이 기능은 플래시에 아무것도 쓰지 않는다.

### 허브에 붙이기

패널은 허브의 주소를 몰라도 된다. 같은 네트워크에 있기만 하면 전체에 대고 부르다가 허브가 답하는 순간부터 허브하고만 이야기한다. 그래서 할 일은 "같은 Wi-Fi에 있게 하는 것" 하나다.

| | 패널에서 할 일 |
|---|---|
| **패널이 이미 쓰는 Wi-Fi에 허브를 넣는다** (공유기 모드, `hub_secrets.h`의 `HUB_STA_SSID`) | 없음. 이미지를 올리면 다시 켜지면서 바로 붙는다. 작업실에서 만지고 디버깅할 때 가장 편하다. 노트북도 같은 Wi-Fi에 있으니 패널의 웹 콘솔과 허브의 콘솔(`http://pf-ensemble.local/`)이 함께 열리고 인터넷도 된다 |
| **전용 공유기를 작업실과 전시장에서 같이 쓴다** | 그 공유기를 패널에 한 번 저장해 두면 끝 |
| **허브의 핫스팟** | 허브의 Wi-Fi를 패널마다 저장한다 (아래) |

패널에 Wi-Fi를 더 저장하는 것도 Wi-Fi로 한다.

```bash
python ensemble/tools/panels.py wifi-add "PatternflowEnsemble" --connect      # 비밀번호는 물어본다
```

`--connect`면 그 자리에서 옮겨 가고, 다음 부팅부터도 그 네트워크를 먼저 찾는다. 빼면 저장만 한다(전시장의 공유기를 미리 넣어 둘 때). 패널은 네트워크를 다섯 개까지 기억하고, 부팅할 때 먼저 찾을 하나(`bootIdx`)가 따로 있다. 한 대만이면 패널의 Wi-Fi 화면에서 넣어도 된다.

**허브가 꺼졌다 켜질 때.** 코어는 네트워크가 사라지면 5초쯤마다 저장된 다음 것을 시도하고, 붙은 곳에 머문다. 15초가 지나도록 못 붙으면 패널 자신의 핫스팟을 연다. 그래서 허브를 다시 굽거나 껐다 켜면 패널들이 작업실 Wi-Fi나 자기 핫스팟으로 가 버린다(2026-11-14에 둘 다 겪었다). 이 이미지(v0.1.2부터)는 그대로 두지 않는다.

- 허브와 함께 있던 패널이 허브 소리 없이 다른 저장된 Wi-Fi에 붙어 있으면, 20초 뒤 그리고 그 뒤로 1분마다 부팅 Wi-Fi(허브의 것)를 다시 시도한다(`PF_ENSEMBLE_HOME_FIRST_MS`, `PF_ENSEMBLE_HOME_EVERY_MS`). 시도하는 동안은 그 Wi-Fi에서 잠깐 빠진다. 켜진 뒤 허브를 아직 못 만난 패널도 켜진 뒤 처음 3분 동안은 같은 식으로 시도한다(`PF_ENSEMBLE_HOME_AFTER_BOOT_MS`). 전원을 한꺼번에 넣으면 패널이 허브의 핫스팟(13초)보다 먼저 켜져 작업실 Wi-Fi로 가 버리기 때문이다. 3분이 지나도 허브가 없으면 혼자 쓰는 패널로 보고 건드리지 않는다.
- 자기 핫스팟에 있을 때 다른 Wi-Fi를 찾는 간격이 5분에서 20초로 줄었다(`PF_HOTSPOT_STA_RETRY_MS`, `panel/bundles/ensemble/overrides.h`).

> 2026-11-14에 겪은 것: 패널의 `POST /api/wifi`에 `connect=1`만 보내면 지금만 옮겨 가고 `bootIdx`는 원래 네트워크에 남는다(Patternflow `core_wifi.h`의 `addNetwork`는 목록이 바뀌어도 원래 고른 네트워크를 따라간다). 그래서 콘솔에서 다시 시작한 패널이 작업실 Wi-Fi로 돌아갔다. 이제 `wifi-add --connect`와 `join`은 `POST /api/wifi/boot`로 그 네트워크를 먼저 정한 뒤 옮긴다. 이미 허브에 있는 패널에 같은 명령을 다시 돌리면 연결은 그대로 두고 `bootIdx`만 바로잡는다.

`patternflow_secrets.h`에 허브의 Wi-Fi를 적어 빌드하는 방법은 **저장된 네트워크가 하나도 없는 패널**(막 지우고 구운 보드)에만 통한다. 하나라도 저장돼 있으면 코어는 컴파일된 것을 쓰지 않는다. 쓰던 패널에는 위의 방법을 쓴다.

### 패널 더 넣기

새 패널에 필요한 것은 셋이다: 이 이미지, 다른 패널과 같은 패턴, 허브의 Wi-Fi. `join`이 이 순서로 한 번에 한다. 새 패널이 원래 쓰던 Wi-Fi(작업실 공유기)에 있고, 노트북도 그 Wi-Fi에 있으면 된다.

```bash
python ensemble/tools/panels.py scan -o new.txt                                          # 새 패널들을 찾아 목록으로
python ensemble/tools/panels.py join $HOME/pf-build/firmware/firmware.bin --file new.txt --pack pack
```

- 이미지는 `flash`처럼 조심해서 올리고, 패턴은 묶음(`pack`, 아래 "패턴 맞추기")과 똑같이 맞추고, 마지막에 허브의 Wi-Fi를 저장해 그리로 옮겨 보낸다. Wi-Fi 이름과 비밀번호는 `hub/hub_secrets.h`에서 읽는다(공유기 모드면 그 공유기). 다른 네트워크면 `--ssid`, `--pass`.
- 한 단계라도 걸린 패널은 허브로 보내지 않는다. 고치고 같은 명령을 다시 돌리면 끝난 일은 건너뛴다.
- 허브의 핫스팟은 8대까지다([6장](#6-몇-대까지)). 노트북도 핫스팟에 들어가면 한 자리를 쓴다.
- Wi-Fi가 하나도 저장되지 않은 패널은 15초쯤 뒤 자기 핫스팟(`patternflow-xxxx`, 비밀번호 `patternflow`)을 연다. 노트북을 그 핫스팟에 넣고 주소 `192.168.4.1`로 `join`한다. 한 번에 한 대다.

### 패턴 맞추기

허브는 패턴을 번호로 보낸다. 패널은 이미지에 든 Origin을 0번으로, 그다음 모듈을 이름순으로(`/patterns/catalog.txt`가 있으면 그 순서로) 번호를 매긴다. 깔린 패턴이 다른 패널이 섞이면 같은 번호가 다른 패턴이 되고, 모듈이 하나도 없는 패널은 Origin만 보인다. 그래서 모든 패널이 같은 패턴을 같은 순서로 갖게 맞춘다. 콘솔에서는 못 한다(패널이 다른 주소의 페이지가 패턴을 올리는 것을 막는다). 패널과 같은 Wi-Fi에 있는 노트북에서 명령 하나로 모두에게 한다.

**다 합쳐서 모두에게** — 가장 간단하고 아무것도 지우지 않는다. Windows에서는 [`tools/sync-patterns.cmd`](tools/sync-patterns.cmd)를 두 번 누르면 끝이다. 명령으로는:

```bash
python ensemble/tools/panels.py --hub-wifi patterns-push --union
```

허브가 아는 패널마다 가진 패턴을 모두 모아(첫 패널의 순서대로, 다음 패널이 더 가진 것은 그 뒤에) `pack-all` 폴더에 묶고, 모든 패널이 그 묶음을 똑같은 순서로 갖게 한다. 패턴이 하나뿐인 패널도 전부 받는다. 패널이 몇 대든 명령은 하나다. 콘솔의 **모든 패널** 칸은 패널마다 패턴 수가 다르면 알려 준다.

`--hub-wifi`는 명령 하나가 도는 동안 이 컴퓨터의 Wi-Fi를 허브의 Wi-Fi(`hub/hub_secrets.h`)에 넣었다가 원래 Wi-Fi로 돌려놓는다(Windows). 패널을 적지 않으면 허브가 아는 패널 모두가 대상이다. 다른 명령에도 붙는다: `panels.py --hub-wifi flash firmware.bin`, `panels.py --hub-wifi status`. 노트북이 이미 허브의 Wi-Fi(또는 공유기 모드의 공유기)에 있으면 `--hub-wifi` 대신 `--hub 192.168.66.1`.

**정해 둔 묶음으로** — 패턴을 골라 두고 그것만 쓰고 싶을 때.

```bash
python ensemble/tools/panels.py patterns-pull 192.168.66.2 -o pack            # 기준 패널의 모듈과 순서를 폴더로
python ensemble/tools/panels.py patterns-pull 192.168.66.3 -o pack --merge    # 다른 패널에만 있는 것도 더하기
python ensemble/tools/panels.py patterns --pack pack --hub 192.168.66.1        # 누가 다른지 (-v 면 무엇이)
python ensemble/tools/panels.py patterns-push --pack pack --hub 192.168.66.1   # 모두 묶음과 같게
```

- `patterns-push`는 없는 모듈만 보내고, 묶음에 없는 모듈은 지우고, `catalog.txt`를 써서 순서를 묶음과 같게 한다. 지울 모듈은 먼저 이 컴퓨터의 `pattern-backup/<패널>-<시각>/`에 받아 둔다. 이미 같은 패널은 건드리지 않는다.
- 같은 이름의 모듈이 패널마다 다른 판이면 각자 가진 것을 그대로 둔다. 묶음의 것으로 덮으려면 `--resend`.
- 묶음 대신 `--from <패널>`을 주면 그 패널에서 받아 바로 나머지에 맞춘다(받은 것은 `pack-<주소>` 폴더에 남는다).
- 이미지에 든 패턴이 다른 패널(다른 에디션)은 맞추지 않는다. 같은 이미지를 먼저 올린다.
- 패널들이 허브의 핫스팟에 있으면 노트북도 그 핫스팟에 들어가야 닿는다(`--hub-wifi`가 해 준다). 유선 인터넷이 있으면 인터넷은 그대로 쓴다.
- 묶음 폴더는 남으니 다음에 패널을 더할 때 `join --pack pack-all`에 그대로 쓴다. 패턴을 더하고 싶으면 한 패널의 `/patterns` 화면에서 올린 뒤 `sync-patterns.cmd`를 다시 누르면 모두에게 간다.

### 원래 펌웨어로 되돌리기

같은 길로 나온다. 원래 쓰던 에디션의 `.bin`을 올리면 된다.

```bash
python ensemble/tools/panels.py flash <원래 에디션의 .bin> --hub pf-ensemble.local     # 허브가 아는 패널 전부
python ensemble/tools/panels.py wifi-forget "PatternflowEnsemble"                       # 허브의 Wi-Fi를 저장했었다면
```

- `--hub`는 허브에게 패널 목록을 물어 온다(`http://<허브>/api/panels`). 허브의 핫스팟에서는 주소가 `192.168.66.1`이다. 이름이 안 풀리는 컴퓨터에서는 허브의 IP를 적는다. 허브 없이 하려면 `scan`으로 다시 찾거나, 콘솔의 **주소 복사**로 모은 주소를 `panels.txt`에 붙여 넣는다.
- 노트북이 인터넷과 패널에 함께 닿는 네트워크에 있으면 [patternflow.work/editions](https://patternflow.work/editions)의 한 번 누르기도 그대로 된다(패널마다 그 패널의 주소를 적는다).
- 패턴, Wi-Fi, 밝기는 그대로다.
- 허브의 핫스팟에 붙어 있는 패널은 인터넷이 없는 네트워크에 있다. `.bin`을 미리 받아 두고 노트북을 그 핫스팟에 넣어 올리거나, 허브를 꺼서 패널이 작업실 Wi-Fi로 돌아온 뒤에 올린다.
- 허브 자체는 Wi-Fi로 굽지 않는다. 노트북에 USB로 꽂혀 있으니 그대로 굽는다.

## 5. 콘솔

[`console/index.html`](console/index.html)을 Chrome이나 Edge로 열고 위쪽에서 고른다.

| | |
|---|---|
| **데모** | 보드 없이 가상 패널로 |
| **USB** | 허브의 USB 잭에 꽂고 누른 뒤 `Patternflow Ensemble` 포트를 고른다(COM 잭의 포트도 된다). Web Serial이라 Chrome·Edge에서만 된다 |
| **Wi-Fi** | 허브의 핫스팟에 들어간 기기에서. 전화기는 그냥 `http://192.168.66.1/`을 열면 허브가 같은 화면을 내준다 |

처음 설치할 때는 이 순서로 한다.

1. 패널을 켠다. 허브에 붙는 대로 지도에 한 줄로 나타나고 번호가 매겨진다.
2. **전체 모양·색 표시**를 누르면 모든 패널이 검은 바탕에 큰 모양 하나를 띄운다. 모양과 색이 번호에 따라 함께 바뀐다: 1 빨강 원, 2 초록 사각형, 3 파랑 삼각형, 4 노랑 원, 5 빨강 사각형, 6 초록 삼각형, 7 파랑 원, 8 노랑 사각형 … 12번까지 모두 다르고, 이웃한 번호는 모양도 색도 다르다. 지도의 타일에도 같은 모양이 같은 색으로 그려지니, 벽의 패널과 지도의 타일을 맞춰 실제 자리로 끌어다 놓는다. 같은 버튼(**표시 끄기**)을 다시 누를 때까지 켜져 있고(잊었을 때를 위해 30분 뒤 저절로 꺼진다), 그 사이 새로 붙는 패널도 제 모양을 띄운다. 한 패널만 보려면 그 패널을 골라 오른쪽의 **표시**(30초). 번호와 이름은 오른쪽에서 바꾼다. 번호를 바꾸면 모양과 색도 따라 바뀐다. (처음에는 빨주노초파남보 여덟 색이었는데, LED에서 빨강과 주황, 파랑과 하늘색이 구별되지 않아 색을 넷으로 줄이고 모양을 더했다. 모양 안의 번호도 멀리서는 검은 덩어리로만 보여 뺐다.)
3. 왼쪽에서 채널마다 단독·동시·물결을 고르고 물결 속도를 맞춘다.
4. 모든 패널의 패턴과 밝기는 왼쪽 맨 위 **모든 패널**에서 한 번에 바꾼다. 패턴은 목록 양옆의 **◀ ▶**로 하나씩 넘기거나(끝에서 처음으로 돈다) 목록을 열어 고른다. 밝기는 지금 있는 패널과 나중에 붙는 패널 모두에게 간다.
5. 패널마다 다른 패턴을 주려면 패턴 규칙을 **단독**으로 두고, 패널을 골라 오른쪽에서 패턴을 정한다(여기도 ◀ ▶가 있다). "이 패널만"은 그 패널만, "여기서 물결로"와 "전체 동시에"는 모두에게 보낸다. 그 패널의 밝기도 오른쪽에서 바꾼다.
6. 마음에 드는 상태는 **장면**에 저장해 두고 불러온다. 고른 패널에서 물결로 불러올 수도 있다. 장면에 밝기는 들어가지 않는다.

배치, 규칙, 장면은 허브의 플래시에 남는다. 노트북을 떼도 허브와 패널만으로 돈다.

아래 로그에는 허브가 겪는 일(패널이 붙음, 끊김, 다시 켜짐)이 찍힌다. "오가는 줄 모두 보기"를 켜면 주고받는 JSON이 그대로 보이고, 입력칸에 한 줄을 써서 직접 보낼 수도 있다. 패널을 고르면 신호 세기, fps, 잃은 보고 수 같은 진단값이 나온다. COM 잭에 시리얼 모니터를 붙여도 같은 줄이 보인다.

## 5½. MIDI

허브는 USB 잭으로 USB-MIDI 장치 **Patternflow Ensemble**이 된다(콘솔의 시리얼 포트와 함께). 2026년 전시의 FlowLocal이 이 보드의 같은 잭으로 Live에 MIDI를 냈던 것과 같은 자리다. 패널은 아무것도 하지 않는다. 주고받는 것은 Patternflow의 MIDI 규약(오디오 에디션의 것, Patternflow `docs/midi-spec.md`)을 패널마다 하나씩 한 것이고, **패널 번호가 MIDI 채널**이다. 코드는 [`core/pfe_midi.h`](core/pfe_midi.h).

| 방향 | 메시지 | |
|---|---|---|
| 앙상블 → Live | CC 24~27, 채널 n | 패널 n의 K1~K4 (0~127). 그 패널이 보여야 할 값이 바뀔 때마다: 그 패널을 손으로 돌렸을 때, 다른 패널의 값이 닿았을 때(동시면 바로, 물결이면 그 패널에 닿는 순간), 장면, 콘솔. 물결은 소리로도 방을 건너간다 |
| | Program Change, 채널 n | 패널 n의 패턴 |
| | 채널 16 | 앙상블 전체를 악기 하나로: 어디서든 방금 돌린 값(또는 콘솔이 보낸 값)이 떠나는 순간 |
| Live → 앙상블 | 채널 1~15 = 그 번호의 패널, 채널 16 = 모든 패널 | |
| | CC 20~23 | K1~K4, 절대값 (0~127 → 0~1000) |
| | CC 24~27 | K1~K4, 상대값 (64 = 그대로, 65 = 한 클릭 위, 63 = 한 클릭 아래) |
| | CC 28 | 밝기 (0~127 → 5~255), 앙상블에만 있는 것 |
| | Program Change | 패턴 |

- Live가 보낸 노브 값은 Live로 되돌려 보내지 않는다(MIDI Thru 없음). 패턴은 원래 규약대로 바뀐 것을 되돌려 보낸다.
- 보내는 것은 대기열이 아니라 상태다. 채널마다, 노브마다 "말할 값"과 "포트가 마지막으로 받아 간 값"을 들고 있다. 그래서 같은 값은 두 번 보내지 않고, 장면처럼 수십 개가 한꺼번에 바뀌어도 빠지지 않는다(USB-MIDI 포트는 한 번에 16개를 받는다. 나머지는 1~2 ms 뒤에 간다). 듣는 프로그램이 없는 동안에는 쌓아 두지 않는다: 누군가 듣기 시작하면 그동안 지나온 값이 아니라 지금 값을 한 번씩 듣는다.
- 16번 패널 이후는 MIDI로 보내지 않는다(채널이 15번까지).
- 버튼(노트 60~63)은 앙상블에 없다.

## 6. 몇 대까지

| 방식 | 패널 수 | |
|---|---|---|
| 허브의 핫스팟 (기본) | **8대까지** | 허브는 핫스팟에 기기를 10대까지 받는다(`HUB_AP_MAX_CONN`, 칩은 15대까지). 그런데 핫스팟의 DHCP 서버가 주소를 8개까지만 기억하고, 아홉 번째가 오면 가장 오래된 것을 잊는다(`CONFIG_LWIP_DHCPS_MAX_STATION_NUM=8`, Arduino 코어에 미리 빌드돼 들어 있는 값). 노트북이나 전화기가 핫스팟에 들어가면 그것도 한 자리를 쓴다. 아홉 번째 기기가 있는 동안 일어나는 일(ESP-IDF 4.4.7 `dhcpserver.c`): 잊힌 패널은 쓰던 주소를 그대로 쓰다가, 임대를 갱신할 때(한 시간쯤 뒤) 거절당하고 새 주소를 받는다. 그때 다른 패널 하나가 잊힌다. 주소는 계속 뒤 번호로 나가다가 100개쯤 나간 뒤 앞 번호로 돌아오는데, 그때부터는 잊힌 패널이 아직 쓰는 주소가 다른 기기에게 갈 수 있다. 그래서 패널 8대일 때 노트북은 잠깐만(`--hub-wifi`가 하는 만큼) 들어가고, 전화기는 붙여 두지 않는다 |
| 공유기 모드 | **24대까지** | 허브와 패널이 모두 보통 Wi-Fi 공유기에 붙는다. 주소는 공유기가 나눠 주니 위의 한도가 없다. `hub_secrets.h`에서 `HUB_STA_SSID`를 켠다. 24는 허브가 기억하는 패널 수(`core/pfe_conductor.h`의 `MAX_PANELS`)다 |

10대 이상이면 공유기 모드로 간다. 2.4 GHz 공유기 하나를 설치 전용으로 두고, 허브와 패널에 그 이름과 비밀번호를 적는다. 패널이 허브를 찾는 방식은 같아서 다른 것은 바꿀 필요가 없다. 콘솔은 그 네트워크의 `http://pf-ensemble.local/`에서도 열린다. 손님용 네트워크처럼 기기끼리 못 보게 막는 설정은 꺼야 한다.

공유기 모드로 옮기는 순서: `hub_secrets.h`에서 `HUB_STA_SSID`와 `HUB_STA_PASS`의 주석을 풀고 허브를 다시 굽는다. 그다음 패널마다 그 공유기를 넣는다. `join`은 `hub_secrets.h`에 공유기가 적혀 있으면 그 공유기로 보낸다. 이미 넣은 패널은 `panels.py wifi-add <공유기> --connect`로 옮긴다.

**24대보다 많이.** `MAX_PANELS`를 올리면 된다. 다만 허브가 패널 목록을 담는 버퍼, 플래시에 저장하는 배치와 장면의 크기, 콘솔 데모의 최대 대수, 24대를 가정한 PC 테스트도 같이 손봐야 한다. 허브의 RAM은 지금 35%만 쓴다. 패널 하나가 1초에 두 번쯤 작은 UDP를 보내니, 50대라도 무선 대역은 남는다. 그때 한도는 공유기다. 집에서 쓰는 공유기는 보통 30~60대에서 불안해지니, 그보다 많으면 기업용 AP를 쓴다. 아직 해 보지 않았다.

**허브의 핫스팟으로 8대보다 많이**는 권하지 않는다. DHCP의 한도를 올리려면 Arduino 코어를 sdkconfig부터 다시 빌드해야 하고, 그래도 칩이 받는 기기는 15대까지다. 공유기를 두는 편이 싸고 확실하다.

## 7. 테스트

```bash
python ensemble/tests/run_tests.py
python ensemble/tests/run_tests.py --patternflow patternflow     # 받아 둔 Patternflow 소스와 훅 순서 대조
```

C++17 컴파일러가 있어야 한다(g++, clang++, 없으면 `python -m pip install ziglang`).

- **core**: 규약의 바이트, 패널 쪽 엔진, 허브를 가상 설치 통째로 돌린다. 동시와 물결의 도착 시간, 엇갈리는 물결, 패킷 30% 손실, 순서가 뒤바뀐 패킷, 패널 전원 재시작, 5초와 12초 Wi-Fi 끊김, 허브 재시작, 24대.
- **panel**: 패널 기능의 기기 쪽(소켓, 프레임 훅, 메뉴 잠금, 번호 표시)을 Patternflow 헤더의 대역(`tests/panel_stub/`)에 대고 컴파일해, 진짜 허브 코드와 맞물려 돌린다.
- **tool**: `tools/panels.py`를 패널 대역(패널의 HTTP 규약대로 답하는 작은 서버)에 대고 돌린다. 잘못된 파일을 보내지 않는지, 이미 올라간 패널을 건너뛰는지, 돌아오지 않는 패널에서 멈추는지. 패턴 묶음을 순서까지 받는지, 맞출 때 없는 것만 보내고 지울 것은 먼저 받아 두는지, `join`이 걸린 패널을 허브로 보내지 않는지.
- **console**: 허브가 내주는 페이지(`hub/src/console_page.h`)가 `console/`과 같은지.

`core/`를 고치면 `python ensemble/tools/build_wasm.py`로 데모를 다시 만들고, `console/`을 고치면 `python ensemble/tools/build_console.py`로 허브의 페이지를 다시 만든다.

  - 일부러 예전처럼 두 코어에 흩어 놓은 빌드(`-DHUB_USB_ONE_CORE=0`)에 같은 부하를 주면 30초에 전송이 199번 멈췄고 199번 모두 다시 걸렸다(줄 4784개, 깨진 줄 0). 한 코어에 모은 빌드에서는 멈춘 적이 없다(`/api/status`의 `usb.rearmed` 0).
  - 한꺼번에 28개가 바뀌는 MIDI(모든 패널의 노브 넷)도 빠지지 않는다. 고치기 전에는 포트가 16개만 받아 마지막 패널의 값이 Live에 안 갔다.
- MIDI: 허브의 USB 잭 하나로 노트북에 `Patternflow Ensemble` MIDI 장치(입력·출력)와 콘솔용 시리얼 포트가 함께 잡혔다. 콘솔이 모든 패널의 K2를 700으로 보내자 채널 16과 채널 1~6에 CC 25 = 89가 나왔고, 한 패널의 패턴을 바꾸자 그 채널에 Program Change가 나왔다. 노트북이 보낸 채널 16 CC 20은 패널의 목표가 되었고 되돌아오지 않았으며, 채널 1·2의 Program Change는 그 패널에 적용되고 규약대로 되돌아왔다. 처음에는 MIDI 장치가 안 보였다: 코어 기본 번호 303A:1001이 S3의 USB-Serial/JTAG와 같아서, 그 장치용 WinUSB 드라이버(oem14.inf)가 MIDI 인터페이스(2번)에 붙었다. 허브의 번호를 303A:8E50으로 바꿔(`HUB_USB_PID`) 풀렸다.
- **패널 여덟 대**(2026-11-14 밤). 여섯 대에 두 대를 더했다. 한 대는 작업실 Wi-Fi에 있던 원래 에디션(3.11.0)이라 `join`으로 넣었고(이미지 → 패턴 56개 → 허브 Wi-Fi), 다른 한 대는 Wi-Fi 설정이 없어 자기 핫스팟(`patternflow-xxxx`, 192.168.4.1)으로만 떠 있어서 노트북이 그 핫스팟에 붙어 같은 일을 했다. 여덟 대 모두 `ensemble v0.1.7`, 패턴 57개(Origin과 모듈 56개)를 같은 순서로 갖고 있고, 허브를 다시 구운 뒤 2분 안에 모두 돌아왔으며, 콘솔에서 넘긴 패턴을 여덟 대가 함께 따라왔다.
  - 모듈이 큰 패널에서 걸린 것: 패널은 모듈 하나를 메모리 한 덩어리에 받는다. 한 시간쯤 자기 핫스팟으로 떠 있던 패널은 가장 큰 덩어리가 51 KB였고, 53 KB짜리 모듈(`midnight_clocktower`) 올리기가 매번 도중에 끊겼다. 다시 켜자 61 KB가 되어 들어갔다. 이제 `patterns-push`와 `join`은 보내기 전에 패널의 `heapLargest`를 보고, 모자라면 패널을 다시 켠 뒤 큰 모듈부터 보낸다.
  - 패턴이 바뀔 때 이름이 안 뜨는 것(v0.1.7)은 PC 테스트로만 확인했다. 패널 화면을 본 것은 아니다.
  - 콘솔의 ◀ ▶는 데모에서 눌러 봤다(빠르게 세 번 누르면 세 칸 간다). 허브에는 같은 명령을 직렬 포트로 보내 여덟 대가 따라오는 것을 봤다.

- 9대째부터의 주소 충돌은 ESP-IDF 소스와 설정값을 읽고 쓴 것이다(6장). 패널 8대에 노트북이 몇 분씩 들어간 것까지는 해 봤고 그동안 탈은 없었다. 실제로 겹치게 해 보지는 않았다.
- 공유기 모드 전체.
- 패턴 번호는 패널마다 같은 패턴이 같은 순서로 깔려 있다고 본다. 처음 묶은 두 패널은 모듈이 34개와 21개로 달랐다. 맞추는 길은 `patterns-push`(4장)다.
- `panels.py`의 `join`, 그리고 묶음에 없는 모듈을 지우는 `patterns-push --pack`은 대역에만 돌려 봤다(위의 `--union`은 실기로 했다).
- Wi-Fi로 되돌리는 길(원래 에디션의 `.bin`을 올리기)은 아직 해 보지 않았다. 올리는 길은 위와 같이 됐다.
- 패널에서 K1을 길게 눌러 바꾼 밝기가 콘솔의 값에 끌려가지 않는지는 PC 테스트로만 봤다.
- 브라우저의 콘솔을 USB 잭의 포트로 붙이는 것. 같은 포트를 Python(pyserial)으로 열어 같은 줄을 주고받은 것까지 확인했다(위). Chrome의 포트 고르기 창은 사람이 눌러야 한다.
- 노트북이 잠들었다 깨어난 뒤의 USB. 코어의 드라이버는 USB 절전을 케이블이 뽑힌 것으로 다룬다. 깨어난 뒤 포트가 안 돌아오면 케이블을 다시 꽂거나 허브를 다시 켠다. 전시 노트북은 잠들지 않게 해 둔다.
- Windows 11 말고 다른 컴퓨터(macOS)에서의 USB 잭.
- 패널 몇 대가 허브에 붙은 채로 보고를 잃던 것(2026-11-14 저녁). 허브를 한 시간 반 사이 열다섯 번쯤 다시 굽고 위의 부하 시험을 한 뒤, 여섯 대 가운데 세 대(3·4·6번)가 초당 하나꼴로 보고를 잃었다(콘솔 로그의 `lost (no report for 3 s)`와 `back`이 번갈아 찍히고, 패널의 `lost`가 계속 는다). 나머지 세 대는 멀쩡했고, 허브의 USB와는 상관이 없었다(USB를 닫아도, 양방향으로 바쁘게 해도 손실은 같았다). 패널이 다시 켜진 것도 아니었다(가동 시간 두 시간 그대로). 4번과 6번은 콘솔에서 재시작시키자 바로 멀쩡해졌고, 3번은 재시작한 뒤에도 남았다. 원인은 모른다. 허브와 같은 채널(6)에 작업실 공유기 둘이 강하게 잡히는 자리였다. 그런 패널이 보이면 먼저 그 패널을 다시 켠다. 같은 날 밤 여덟 대에 v0.1.7을 올리고 허브를 다시 구운 뒤에는 3번을 포함해 여덟 대 모두 1분 동안 잃은 보고가 0이었다.
- 모양 표시(원·사각형·삼각형 × 빨강·초록·파랑·노랑)를 실제 패널에서 본 것. 색만 쓰던 v0.1.3까지는 실기로 확인했다.
- 켜진 직후 3분 동안 허브 Wi-Fi로 돌아가기(v0.1.6)를 전원을 한꺼번에 넣어 본 것.
- 허브가 오래(1분 넘게) 꺼져 있다 켜질 때. 패널은 그동안 작업실 Wi-Fi와 허브의 Wi-Fi를 1분마다 오가며 찾는다. 허브 없이 다시 켠 패널은 허브를 찾아 나서지 않는다(혼자 쓰는 패널로 본다).
- `sync-patterns.cmd`를 두 번 눌러 돌리는 것. 같은 명령(`--hub-wifi patterns-push --union`)의 두 부분은 따로 실기로 돌렸다.

들어 있지 않은 것:

- 전시 패널에 있던 Wi-Fi 자가 복구(연결은 됐는데 허브가 안 들릴 때 다시 붙기)는 코어를 고쳐야 해서 뺐다.
- 허브의 채널 자동 선택. 채널은 `HUB_AP_CHANNEL`(6)로 고정이다.
- 일정 시간 뒤 처음 상태로 돌아가기(전시의 3분 복귀).
